## Q1（2026-10-17）：HTTP 方法的幂等性是什么？

### 问题背景

学习 `STUDY_GUIDE.md` 核心知识点 2「HTTP 方法语义与幂等性」时，需要系统理解幂等性的定义和应用。

### 结论要点

**定义**：同一个请求执行一次和执行多次，对服务端资源的**最终效果相同**。幂等 ≠ 只能调用一次，而是"调用 N 次 = 调用 1 次"。

**各方法判定**：

| 方法 | 安全 | 幂等 | 说明 |
|------|------|------|------|
| GET | ✅ | ✅ | 只读，不改变资源 |
| HEAD | ✅ | ✅ | 同 GET，只返回头 |
| PUT | ❌ | ✅ | 整体替换为指定内容，第 2 次替换结果一样 |
| PATCH | ❌ | ❌* | 局部更新（如 `count+1` 不幂等；*全量覆盖式 PATCH 可以幂等） |
| DELETE | ❌ | ✅ | 删完再删，资源仍不存在（最终状态一致） |
| POST | ❌ | ❌ | 创建资源，每次调用产生新资源/新订单 |

**为什么 PUT/DELETE 幂等而 POST 不是**：

- **PUT**：语义是"把资源设置成 X"，不管执行几次，资源都是 X。
- **DELETE**：语义是"移除资源"，删除操作对不存在的目标是 no-op。
- **POST**：语义是"提交/创建"，每次调用服务端都要做一次新处理（生成新 ID、追加记录），重复调用产生重复效果。

**为什么这是核心考点（幂等与重试）**：

网络超时后无法知道请求是否已到达服务端：

- GET/PUT/DELETE：放心自动重试，不会造成副作用。
- POST：盲目重试会造成重复下单/重复注册，必须靠**幂等键（Idempotency Key）**——客户端生成唯一 key，服务端据此去重。

**两个常见追问**：

1. **重定向与幂等**：301/302 会把 POST 转成 GET（改变语义），307/308 保留方法——所以 POST 重定向要用 307/308，否则重试链路会丢掉请求体。
2. **GET 幂等但不安全**：幂等只说"重复无害"，安全说"不修改资源"——GET 可能有副作用（如 GET /delete?id=1 是反模式），它幂等只是碰巧删的是同一个东西。

## Q2（2026-10-17）：PUT 每次替换不同内容，不就非幂等了吗？

### 我当时的理解（有偏差）

> PUT 和 POST 都是更新资源，只不过 PUT 是替换、POST 是新增。但如果 PUT 每次都替换不一样的内容，重复执行效果不同，不也是非幂等了吗？

### 纠正后的理解

- 幂等性比较的是**同一个请求**重复执行 N 次 vs 执行 1 次的效果，不是**不同请求**先后执行的效果。
- "每次替换不同的内容"意味着请求体不同，那已经是两个独立的新请求，根本不在幂等性的讨论范围内。
- 幂等性只回答一个实际问题：**网络超时后，把刚才那个一模一样的请求原封不动再发一遍，安全吗？**

### PUT vs POST 的幂等本质（资源标识由谁决定）

| | URL 是否含资源 ID | 语义 | 重复同一请求的后果 |
|---|---|---|---|
| PUT | 是（`/articles/42`） | 把 42 号"设置为 X" | 还是 X → 幂等（且 URL 钉死了操作对象，也能 upsert 创建） |
| POST | 否（`/articles`） | "创建一个新的" | 每次分配新 ID → 产生多个资源 → 不幂等 |

### 逐例对照

```text
PUT /articles/42   body: {title: "A"}  → 资源变成 {title: "A"}
PUT /articles/42   body: {title: "A"}  → 资源还是 {title: "A"}  ← 重复同一请求 → 幂等
PUT /articles/42   body: {title: "B"}  → 资源变成 {title: "B"}  ← 另一个新请求，无所谓幂等

POST /articles     body: {title: "A"}  → 创建文章 id=1
POST /articles     body: {title: "A"}  → 又创建文章 id=2       ← 同一请求重复 → 不幂等
```

### 第一句话的修正

> "PUT 是替换资源，POST 是新增资源" → 更准确的说法是按 **URL 语义**区分：

- PUT：URL 含资源 ID，典型用途是全量更新（替换），但也能创建（upsert，资源不存在就创建）。
- POST：URL 指向集合，专门用于创建 / 子操作。

### 面试追问预演

- **Q：PUT 内容每次都不一样，还幂等吗？**
  A：内容不同 = 不同请求，不在幂等讨论范围；幂等只看同一请求重复重发是否安全。
- **Q：GET 幂等是不是也安全？**
  A：不是。幂等（重复无害）和安全（不修改资源）是两个独立属性；GET 带副作用（如 GET /delete?id=1）是反模式，它幂等只是因为删的是同一个东西。

## Q3（2026-10-17）：为什么对称加密比非对称加密传输效率高？

### 问题背景

学习 HTTPS 的加密分工（STUDY_GUIDE 核心知识点 3）时的追问：既然都能加密，为什么非对称加密不能直接传业务数据？

### 结论要点

**核心原因：两者的数学运算复杂度完全不在一个量级。**

**1. 运算本身的代价不同**

| | 对称加密（如 AES） | 非对称加密（如 RSA/ECDHE） |
|---|---|---|
| 核心运算 | XOR、位移、查表（SP 网络/Feistel） | 大数模幂（RSA）、椭圆曲线点乘（ECDHE） |
| 单次操作成本 | 极低（CPU 有 AES-NI 专用指令） | 极高，比对称慢 **100~1000 倍** |
| 密钥规模 | 128/256 bit | RSA 至少 2048 bit |

直观感受：AES 加密 1GB 数据在现代 CPU 上不到 1 秒；RSA 做一次加密/签名就要几十毫秒，直接加密 1GB 要算几小时。

**2. 设计目标不同，注定复杂度不同**

- 对称加密：双方已共享密钥，只需保证"有密钥的能算、没密钥的算不动"，可用廉价数学操作（混淆+扩散），效率优先。
- 非对称加密：要解决"无共享密钥时如何安全交换"，必须依赖**单向陷门函数**（乘法容易、因数分解难；椭圆曲线点乘容易、求离散对数难）。安全性正是建立在"运算本身困难"上，快不了。

**3. 密钥长度放大差距**

对称密钥 128 bit 已足够安全；RSA 因大数分解算法进步，至少要 2048 bit——操作数大几个数量级，模幂代价随之爆炸。非对称用"长密钥"换安全，用"慢"买单。

**4. HTTPS 分工由此而来**

- 握手阶段（少量数据）→ 非对称：贵但只做几次，用来安全传递对称密钥。
- 通信阶段（海量数据）→ 对称：便宜，撑得住高吞吐。

一句话总结：**非对称加密贵在"建立信任"，对称加密便宜在"批量干活"——HTTPS 用非对称做密钥交换、对称做数据传输，各取所长。**

### 面试追问预演

- **Q：为什么不能全程用对称加密？**
  A：因为双方事先没有共享密钥，如何在不安全信道上把对称密钥安全地交给对方，这就是"密钥交换问题"，只能靠非对称加密解决。
- **Q：AES 为什么那么快？**
  A：运算以 XOR/查表为主，且现代 CPU 有 AES-NI 硬件指令集，单条指令完成一轮变换。
- **Q：非对称慢的数学根源是什么？**
  A：依赖"容易正算、极难反算"的单向陷门函数——RSA 是大整数乘法容易、质因数分解难；ECDHE 是椭圆曲线点乘容易、离散对数难。
