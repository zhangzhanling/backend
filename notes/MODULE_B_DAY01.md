### Q0（示范题，已给参考答案）：为什么选 PostgreSQL 而不是 MySQL？

**1. 功能丰富度**

- CTE、窗口函数、递归查询、FILTER 子句是 PG 的一等公民；MySQL 8 才补窗口函数，优化器处理复杂查询长期弱于 PG。
- jsonb 支持索引（GIN）和丰富操作符，适合文档元数据、AI 中间结果等半结构化数据。
- 部分索引、表达式索引（如只给未删除行建索引）MySQL 做不到。

**2. 对主项目的决定性因素：AI 能力**

- pgvector：向量检索直接在 PG 内完成，业务数据 + 向量数据一个库，架构简单、事务一致——选 PG 最硬的理由。
- 内置全文检索（tsvector），关键词 + 向量的混合检索可在一个库完成。

**3. 事务与 DDL 的工程品质**

- PG 的 DDL 大多支持事务（建表改表可回滚），MySQL 的 DDL 隐式提交。
- PG 的 MVCC 与隔离级别语义更"正统"，B4 学事务时更有教材价值。

**4. 约束与数据严谨性**

- CHECK 约束在 MySQL 8.0.16 之前被静默忽略；PG 的约束、外键、触发器一直完整可靠。

**MySQL 的优势（面试必须会答的另一半）**

- 国内岗位存量大、招聘频率高；运维生态成熟（主从复制、中间件、云平台）；简单 CRUD 高并发口碑好。

**回答结构**：先给结论 → 列对方优势 → 说明迁移成本。两者底层概念（B-tree、MVCC、事务、锁）完全相通，学 PG 不放弃 MySQL 岗位，差异在优化器行为、DDL 事务性、运维生态。

### Q1. 关系型数据库里的"关系"指的是什么？

### Q2. 主键的作用是什么？

如果一张表不建主键，会发生什么实际问题？

> **标准答案：** 主键的作用是让每一行全局可寻址。不建主键的实际问题：① UPDATE/DELETE 无法保证只命中目标行，可能批量误改误删；② 复制与 CDC 工具（binlog / Debezium / 逻辑复制）对无主键表的 UPDATE/DELETE 报错，或需 REPLICA IDENTITY FULL；③ ORM/应用层普遍要求唯一标识；④ 外键必须引用唯一列；⑤ 排障时无法定位"是哪一行"。一句话：应用/ORM/复制/审计/排障都依赖主键。与 UNIQUE 索引的区别（4 层）：① 语义不同——主键 = 行身份，唯一且隐含 NOT NULL，一张表一个；UNIQUE 可空、可多个，表达业务唯一性；② 系统默认认主键——外键引用目标、CDC replica identity；③ 实现上 PG 的主键就是一个 NOT NULL UNIQUE B-tree 索引，显式声明是写进 schema 的语义承诺；④ 一句话总结：主键是约束语义，UNIQUE 是数据规则。

### Q3. 主键用自增 ID（identity/bigserial）还是 UUID？

各自有什么优缺点？你在自己的项目里会怎么选，为什么？

> **标准答案：** 自增 ID（bigint）优点：简单、省空间、时间有序（写入局部性好）。缺点：① 可枚举 → IDOR 水平越权风险（遍历 /resource/1..N 拖走全库，泄露业务量只是次要风险）；② 分布式/多库合并会冲突，需发号器（雪花 ID）；③ 高并发追加造成写入热点（索引最右页）。UUID v4 优点：全局唯一无中心、可预生成、不暴露顺序数量；缺点：随机值打散 B-tree（页分裂、缓冲命中率差）、占 16 字节；折中方案 UUID v7 / ULID（时间有序）。选型口诀：单体 + id 不对外 → bigint；id 进对外 URL 或需预生成 → UUID v7。更成熟的做法：内部自增 bigint + 对外随机 token 列（share_token，可挂过期/次数限制）。关键认知：随机 id 只是抬高枚举成本，不能替代授权校验——IDOR 的根本修复是对象级权限校验（WHERE 带 owner 或取出后比对），随机 id 与权限校验是纵深防御的两层，都做。

> 我的回答：自增 ID 优点是逻辑简单、占用空间少；缺点不确定。UUID 优点不确定；缺点是算法复杂、占用空间多。
>
> 批改记录：⚠️ 一半（2026-10-31）。自增缺点核心三项：① 暴露信息量（id 可枚举 → 遍历爬取/IDOR，暴露业务量）② 分布式下冲突，需发号器（雪花）③ 写入热点（高并发追加索引最右页）。UUID 优点：① 全局唯一无中心，多库合并/客户端预生成可行 ② 不暴露顺序数量。补：随机 UUID v4 打散 B-tree → 页分裂、缓存差 → UUID v7（时间有序）/ULID 折中。
> 选型口诀：单体+id 不对外 → bigint；id 进对外 URL/分布式 → UUID v7；折中 → ULID。
> 重答（2026-10-31）：user 表 → 自增（理由：用户量不大、无分库分表/高并发）；resources → UUID（理由：数量可能很多、涉及批量新增）。→ ⚠️ 选型基本合理，理由需精修。
> 精修 1：自增 ID 的数据量上限不是瓶颈（bigint 足够），选型轴是"对外暴露面"和"预生成/分布式需求"，不是数据量。
> 精修 2：resource 选 UUID 的正当理由 = ① 异步导入管道需写入前预生成 id（关联文件/任务、幂等去重）② 资源链接可能对外分享。
> Q3-追问（2026-10-31）："暴露数据量；可用雪花 ID 缓解。" → ❌ 部分正确。漏了核心风险：**可枚举 → IDOR 水平越权**（遍历 `/resource/1..N`，漏检权限即读到他人资源；泄露业务量只是次要）。雪花 ID 答错：它解决分布式生成，且时间有序仍可估算增长、可枚举，不是安全方案。
> 正确缓解手段：**内部标识与对外标识分离**——内部主键自增 bigint，对外用随机 token 列（share_token），URL 只出现 token；可挂过期/次数。比全表 UUID 更成熟。
> 记忆点：随机 id 只是提高枚举成本，不能替代授权校验。
> 补充讲解（2026-10-31）：IDOR = 不安全的直接对象引用（OWASP；API 场景称 BOLA）。定义：请求携带对象标识，服务端只验证登录、未验证对象归属 → 改 id 即可越权访问他人数据。例：`GET /api/resources/1024` 合法，遍历 1..N 拖走全库。关键认知：随机 UUID 不修复 IDOR，只是抬高枚举成本；根本修复 = 对象级权限校验（WHERE 带 owner 或取后比对）。防御三件套：对象级授权校验 / 自动化越权测试 / 随机 token 缓解。模块 D 将实际写越权测试。
> 延伸问答（2026-10-31）：做了对象级权限检查后自增 id 还有影响吗？→ 越权风险基本消失，但残留两类泄露：① 业务量/增长趋势泄露（竞品数人头，很多公司换 UUID 的真实动机）② 存在性探测与公开资源批量爬取。
> 原则：**纵深防御（Defense in Depth）**——权限检查是根本修复（赌每行代码不出错），随机 id 抬高攻击成本（每层都提高成本），两者解决的问题不同，都做。面试加分句。
> 重答（2026-10-31）："内部使用自增 ID，外部分享使用随机 token，加上访问次数和访问时间限制。" → ✅ 完全正确，三要素齐全（内部自增 / 外部随机 token / 次数+时间限制）。Q3 全部闭环。

### Q4. 为什么存金额不能用 float / double，要用 numeric / decimal？

底层原因是什么？

> **标准答案：** float / double 是 IEEE 754 二进制浮点，大部分十进制小数（如 0.1）的二进制表示是无限循环 → 存储时截断 → 误差累积，连比较都会失效（0.1 + 0.2 == 0.3 为 false）。numeric / decimal 是十进制定点存储，天然精确，代价是计算较慢。替代方案：按最小货币单位用整数存分。

> 我的回答：金额涉及到计算，float 和 double 都不能实现精确计算，可能会有误差。
>
> 批改记录：⚠️ 方向对，缺底层（2026-10-31）。核心：float/double 是 IEEE 754 二进制浮点，大部分十进制小数（如 0.1）二进制表示无限循环 → 截断存储 → 误差累积；连比较都失效（0.1+0.2==0.3 为 false）。numeric 是十进制定点存储，天然精确，代价是计算较慢。替代方案：按最小货币单位用整数存分。

### Q7. 什么场景下考虑用 jsonb 列，而不是把字段拆成正常的列？

> 我的回答：先要求讲解 jsonb 概念（2026-10-31）。
>
