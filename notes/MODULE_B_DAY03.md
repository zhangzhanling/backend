### Q1. 一对多（1:N）关系怎么建模？

外键应该放在哪一边？为什么？（例：一个用户拥有多个 resource）

> **标准答案：** 外键放在"**多**"的那一端。本质：一列只能存一个值，"多"端每行恰好只有一个父，外键天然成立；反向"一"端的一列装不下多个子 id。核心原则：**关系只存一遍**，"一"端的名单通过 WHERE / JOIN 查询反向推导、总数通过 COUNT——不要在"一"端冗余存子 id 列表。

> 我的回答：一对多关系，外键应该放在"多"的表中。比如一个老师有多个学生，学生表中有个外键关联老师。
>
> 批改记录：✅ 正确（2026-11-03）。本质：列只能存一个值，"多"端每行恰好只有一个父，外键天然成立；反向一列装不下。
> Q1-追问（2026-11-03）："'一'端通过查询学生表 WHERE teacher_id = 当前老师，计算总数。" → ✅ 正确，Q1 闭环。核心原则：**关系只存一遍，'一'端通过查询'多'端反向推导**（名单 = WHERE/JOIN，总数 = COUNT）。
> ✅ Q1 闭环。

### Q2. 多对多（M:N）关系怎么建模？

为什么不能把多个 id 用逗号分隔存在一个字段里（如 `resource.tag_ids = '1,2,3'`）？（答完做实验 1，你会亲眼看到这种设计的灾难）

> **标准答案：** 正确方案 = **关联表** article_tag(article_id, tag_id)：M:N 物理上是两个 1:N，配套双外键（ON DELETE CASCADE）+ **(article_id, tag_id) 复合主键**防重复、双向查询有索引。口诀：关联表 = 两个外键 + 一个复合主键。逗号列表损失数据库三大能力：① **查询正确性**（LIKE '%2%' 会误命中 '12'，结果直接错）；② **约束失效**（外键 / 唯一 / NOT NULL 对字符串内部全部无效）；③ **索引失效**（无法索引字符串片段）。本质：数据降维成文本，数据库对文本内部无能为力。

> 我的回答：文章表存标签 id，标签表存文章 id。不知道为什么不能用逗号分隔，难道不好查询？
>
> 批改记录：❌ 建模错误 + 理由低估（2026-11-03）。① 正确方案 = **关联表** article_tag(article_id, tag_id)：复合主键防重复、双外键（ON DELETE CASCADE）、M:N 物理上是两个 1:N。双向存列表 = 逗号灾难×2。② "不好查询"严重低估：损失的是数据库三大能力——**查询正确性**（LIKE 误匹配，结果直接错）、**约束**（外键/唯一/NOT NULL 对列表内部全部无效）、**索引**（无法索引字符串片段）。本质是"数据降维成文本，数据库对文本内部无能为力"。
> 重答（2026-11-03）：实验确认——LIKE '%2%' 把文章C（tag_ids='12'）误命中，查询结果错误。正确建模 = 关联表 + 双外键；损失三条 = 查询正确性（模糊匹配出错）、约束失效（外键/唯一无法作用于列表内部）、索引失效（无法索引字符串片段）。→ ✅ Q2 闭环。
> 补充设计细节：关联表需加 (article_id, tag_id) 复合主键——防重复 + 双向查询有索引。口诀：**关联表 = 两个外键 + 一个复合主键**。

### Q3. 一对一（1:1）关系怎么建模？什么场景才值得拆出 1:1？

（提示：什么情况下你会把一张表竖着切成两张一对一的表？）

> 我的回答：一对一关系，在其中一个表里面新建外键关联另一个表即可。什么场景一张表切成 2 张表，不知道。
>
> 批改记录：⚠️ 一半 + 盲区（2026-11-05）。① 建模漏零件：只建外键 = 1:N；1:1 完整配方 = **外键 + UNIQUE**（如 user_profile.user_id 直接当主键兼外键，FK² 口诀）。② 竖切三场景：冷热分离（大文本/低频字段拆出，如 document 元数据 vs document_content 全文——列表查询不被大文本拖慢）、敏感字段隔离（密码哈希等拆出做细粒度权限）、可选扩展防 NULL 泛滥（没填的人没有行，比一行全 NULL 干净）。代价：每次完整数据需 JOIN，别为拆而拆。
> 重答（2026-11-05）：FK² 配方 ✅（一端主键唯一 + 另一端外键引用；小修：外键列自身也要唯一，通常直接当主键）；竖切场景：① 冷热分离 ✅（content 大字段拆出，否则影响索引、查询变慢）② 权限管控 ✅（密码 hash 拆出控制读写权限）。
> Q3-追问（2026-11-05）："正文该拆——同表会查询变慢、列表查询缓冲区被正文污染。" → ✅ 正确，Q3 闭环。补充：PG 大字段自动 TOAST 压缩存外部，列表查询仍 touch 行（缓冲/IO 吃亏），拆 resource_content 成立；TOAST 被追问算加分项。

### Q4. 什么是规范化？1NF / 2NF / 3NF 各用一句话讲清

（不用背定义，各举一个违反的例子再修正，才是真懂）

> 我的回答：知识盲区（2026-11-05 首答）。
>
> 概念讲解：规范化治三种病——冗余、更新异常（改一处漏一处→自相矛盾）、删除异常（删 A 带走 B）。
> 1NF：字段原子不可再拆。反例：tag_ids='1,2,3'（Day 3 实验 1 的灾难）→ 拆关联表。
> 2NF：非主键列必须依赖整个主键（针对复合主键），不能只依赖一部分。反例：order_item(order_id, product_id 复合主键, ..., product_name 只依赖 product_id → 部分依赖) → 拆 product 表。
> 3NF：非主键列之间不得传递依赖（A→B→C）。反例：user(id, city, city_zipcode)——zipcode 依赖 city 而非 id → 拆 city 表。
> 工程惯例：一般做到 3NF；再往下是刻意反范式（Q5）。
> 重答（2026-11-05）：1NF/2NF/3NF 各一句 + 反例齐全（tag_ids 逗号灾难 / order_item 冗余 product_name / user 表 city_code 传递依赖）。→ ✅ Q4 闭环。措辞微调：3NF 表述为"city_code 依赖 city 而非 id，构成传递依赖，需拆 city 信息到独立表"。

### Q5. 反规范化什么时候值得做？代价是什么？

（提示：什么查询痛点会让人愿意冗余数据？冗余之后的一致性谁来保证？）

> 我的回答：知识盲区（2026-11-05 首答）。
>
> 概念讲解：反规范化 = 有意违反范式冗余数据，换查询速度。动机 = 消除两类查询代价：① JOIN 代价（冗余字段，如 order 存 buyer_name）② 实时聚合代价（冗余计数器，如 post.comment_count）。
> 代价三层：① 一致性成本（核心）——信息存两处，写必须同事务同时成功；② 更新异常回归（范式化治好的病回来了）；③ 同步责任在应用层事务/触发器，做不到实时则退化为最终一致性。
> 决策标准：读多写少 + 热点明确 + 聚合实测昂贵 → 值得；写多/数据量小/一致性敏感 → 别做。纪律：先规范化后按需反范式；每处冗余文档化同步策略（面试官必问"冗余字段怎么保证一致"）。
> 重答（2026-11-05）：两形态（冗余字段消 JOIN / 冗余计数器消实时聚合）✅；三层代价 ✅；决策标准 ✅；应用题：不做（数据量小 + 实时查询代价可控）✅ → Q5 闭环。一词之修："优化器"应为"触发器"。

### Q6. 逻辑删除（deleted_at）vs 物理删除，怎么选？

逻辑删除引入后，查询、唯一约束、索引会发生什么变化？（这是逻辑删除的三个经典坑）

> 我的回答：根据业务场景决定，需要彻底删除用物理删除，否则逻辑删除。坑 1：每次查询都要加 where 条件；坑 2：新用户注册同一 email 需要业务层做约束；坑 3：表越来越大，查询变慢、索引效率低。
>
> 批改记录：⚠️ 一半（2026-11-05）。第一问太虚——判据要落地：逻辑删除 = 需误删恢复/审计追溯/防悬挂引用；物理删除 = 合规彻底删（注销、GDPR/个保法）/垃圾数据。同一系统两种并存是标准答案（主项目：resource 逻辑删 + 用户注销物理删）。
> 坑 1 ✅ 精修：漏加 WHERE deleted_at IS NULL = 线上 bug；工程解法 ORM default scope / 统一视图。
> 坑 2 ❌ 方向反了：不是业务层加约束，而是 **UNIQUE(email) 拦住新用户**（老用户行还在，新注册撞 unique violation）。解法 = **部分唯一索引**：CREATE UNIQUE INDEX ... ON users(email) WHERE deleted_at IS NULL（只对活行唯一，PG 招牌能力）。
> 坑 3 ✅ 补：死数据撑大表+索引；解法 = 定期归档/延迟物理清理（如 90 天后真删），逻辑删除是缓兵之计。
> 重答（2026-11-05）：逻辑删除判据（可反悔防误删/审计追溯/被引用）✅；物理删除判据（注销账号/隐私数据/过期日志）✅；坑 2 修正（UNIQUE 在数据库层拦住新注册；解法 = 部分唯一索引）✅ → Q6 闭环。

### Q7. 结合主项目：找出所有 M:N 关系

为「收藏集（collection）↔ 资源（resource）」设计关联表：表名、列、主键、唯一约束、外键及 ON DELETE 行为——每个决策说理由。

> 我的回答：表 collection: id(主键)、title、description、collection_time、user_id(外键)；表 resource: id(主键)、title、context、collection_id(外键)、category。ON DELETE 采用级联删除。
>
> 批改记录：❌ 核心错误（2026-11-05）——把 M:N 退化回 1:N：resource 加 collection_id = 一个资源只能进一个收藏集。正确 = collection_item 关联表：collection_id(FK→collection, ON DELETE CASCADE) + resource_id(FK→resource, ON DELETE RESTRICT) + created_at，复合主键 (collection_id, resource_id) 防重复收藏。resource 上不该有 collection_id；resource.user_id 表资源主人，collection.user_id 表收藏集主人（可收藏他人资源）。
> 两外键 ON DELETE 不同的理由（Day 2 决策树回收）：collection 删→条目随之清（CASCADE）；resource 被收藏时删→RESTRICT 抛矛盾（用户数据不被静默吞掉）。

### Q8. 建模综合题：标签（tag）系统设计

需求：一个用户可以给 resource 打多个标签，一个标签可以被多个 resource 使用；要求"同一用户下标签名唯一"；要能查出"某个标签下的所有资源"和"某资源的所有标签"。

请你建模：几张表、什么关系、哪些约束？然后回答：如果需求改成"标签全局共享（不区分用户）"，设计变哪里？

> 我的回答：resource(id, title, desc, created_at)；resource_tags(主键 id, tag_id)；user_tags(主键 user_id+tag_id)；tags(id, title, created_at)。
>
> 批改记录：❌ 四表设计有误（2026-11-05）。① resource_tags 缺 resource_id——不表达任何关系；② user_tags 冗余——"用户拥有标签"是 1:N，tag 表加 user_id 列即可（1:N 不需要关联表）；③ resource 缺 user_id；④ tag 缺核心约束 UNIQUE(user_id, title)。
> 正确 = 3 表：resource(user_id FK)；tag(user_id FK + UNIQUE(user_id,title) = 需求落点) 1:N user→tag；resource_tag(resource_id FK CASCADE, tag_id FK CASCADE, 复合主键) M:N resource↔tag。两查询靠复合主键双向索引。两外键均 CASCADE（关系双方同属一个用户，无第三方受损）。
> 变化题（全局共享）：tag 去 user_id，UNIQUE(title) 全局唯一。本项目选"每用户独立"——标签是个人分类体系，全局共享引入标签治理成本（重名/权限/垃圾标签），单人项目负资产。
> 待重答：三表关系复述 + UNIQUE 防什么 + 变化题两句。

## 任务 2：验证实验（20 分钟，答完 Q2 后做）

  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title text NOT NULL,

  ('文章A', '1,2'),
